## Codebase Map
`models.py` defines 7 SQLAlchemy models: `User`, `Tag`, `Song`, `ListeningEvent`, `Rating`, `Playlist`, `Notification`.
- The `friendships` table is a join table that represents the relationships between many users to many users.
- The `song_tags` table is a join table that joins songs with multiple tags.
- The `playlist_entries` table is a join table that adds a `position` column, a song entry in a playlist has its own position, not just insertion order.

2. Listing friends listening now: `GET feed/<user_id>/listening-now` in `routes/feed.py` calls `feed_service.get_friends_listening_now`. That function loads the `User`, collects `user.friends` IDs, and queries `ListeningEvent` filtered to those friend IDs where `listened_at` is within the last 24 hours (`RECENT_THRESHOLD`), ordered most-recent first. It walks the results and keeps only the first event per friend (dedup via a `seen_friends` set), hydrating the `User` and `Song` for each kept event, and returns a list of `{friend, song, listened_at}` dicts. The route wraps it as `{"feed": [...], "count": N}`.
3. Searching a song: `GET songs/search?q=<query>` in `routes/songs.py` calls `search_service.search_songs`. That function builds a SQLAlchemy query on `Song` with an outer join to the `song_tags` association table and filters where `Song.title ILIKE %query%` OR `Song.artist ILIKE %query%` (case-insensitive substring match), then serializes each matching `Song` with `song.to_dict()` (which includes the associated tag names). The route returns `{"results": [...], "count": N}`, or 400 if `q` is missing.
4. Rating a song: `POST songs/<song_id>/rate` with JSON `{user_id, score}` in `routes/songs.py` calls `notification_service.rate_song`. That function validates `1 <= score <= 5`, loads the `Song` and rating `User`, then checks for an existing `Rating` matching `(user_id, song_id)`: if found it mutates its `score` in place (upsert), otherwise it constructs and adds a new `Rating`. It commits and returns the `Rating`, which the route serializes with `.to_dict()` and returns as HTTP 201. Note: despite living in `notification_service.py`, this path does not currently create a `Notification`.
5. Listing all song entries in a playlist: `GET playlists/<playlist_id>/songs` in `routes/playlists.py` calls `playlist_service.get_playlist_songs`. That function loads the `Playlist`, then queries `Song` joined to the `playlist_entries` association table filtered by `playlist_id` and ordered by `playlist_entries.position ASC`, and serializes each `Song` via `to_dict()`. The route returns `{"songs": [...], "count": N}`.

A song gets added to a user's feed: the feed is not a stored table — it's derived at read time from `ListeningEvent` rows written when a friend records a listen. `POST songs/<song_id>/listen` with JSON `{user_id}` in `routes/songs.py` calls `streak_service.record_listening_event`. That function loads the listening `User`, constructs a `ListeningEvent(user_id, song_id, listened_at=now)` and stages it with `db.session.add`, then calls `update_listening_streak(user, now)` to bump `user.listening_streak` / `user.last_listened_at` (start at 1, +1 if yesterday, reset to 1 otherwise), and finally `db.session.commit()`s both writes together. From that point on, when any friend of this user hits `GET feed/<friend_id>/listening-now`, `feed_service.get_friends_listening_now` (flow 2) will pick up the new `ListeningEvent` — provided it falls within the 24-hour `RECENT_THRESHOLD` and is the friend's most recent event — hydrate the `User` and `Song`, and include it as a `{friend, song, listened_at}` entry in that friend's feed.
